## 二、架构决策：Screener 重构方案（方案 A）

### 2.1 核心问题

当前系统存在两套路由并行：

- **新架构**（pipeline.py + action_router.py + strategies/）：Style → Action → EntryGen，已注册 18 个 EntryGen，SCREENER_REGISTRY 全空
- **旧架构**（selector.py 2052行）：cycle_phase + invest_style → if-elif 大函数，只认旧4值

影响：新架构产出 10+ 种 Style，旧 selector 不认识 → 大量日子 return [] → 空仓率 59.3%

### 2.2 决策：方案 A — Screener 留在 Pipeline 外

**Pipeline 不改**。Pipeline 的唯一职责：接收单只股票的 MarketContext，输出 BuyPointPlan。

**Screener 作为独立算子**，与 EntryGen、ExitEngine 平级。由 trade_plan.py 编排调用顺序。

**不走方案 B**（把 Screener 塞进 Pipeline）：会让 Pipeline 职责复杂化，违背"策略函数只做计算"原则。

### 2.3 最终架构

```
trade_plan.py（编排层）
  |
  +-- 1. 查表确定 screener_name
  |     action_router.resolve(ctx) -> (action, screener_name, entry_name, pos_mult)
  |     只用 screener_name，entry_name 由 pipeline 内部处理
  |
  +-- 2. 调用 Screener（全局选股）
  |     SCREENER_REGISTRY[screener_name](market_data) -> [候选股列表]
  |
  +-- 3. 对每只候选股:
       +-- _build_context(stock) -> MarketContext
       +-- DecisionPipeline.process(ctx)
            +-- Step 1: _route(ctx) -> 内部决定 entry_name（不变）
            +-- Step 2-9: EntryGen + 止盈止损 + 仓位（不变）
            +-- 返回 UnifiedPlan
```

**关键原则**：
- Pipeline 内部路由保持不变（`_route()` -> `action_router.resolve()`），不改为外部注入 entry_name
- Screener 注册到 SCREENER_REGISTRY，trade_plan.py 通过注册表调用
- 逐 action 重构，每改一个注册一个，最后删除旧 `select_stocks()`

3. 模式A 优先：如果前序有 confirmed/early 主线且 D 日主线切换，优先选旧主线的回调龙头
4. 模式B 兜底：如果没有明确旧主线，从 D 日 theme_top 中排名跳升最大的板块中选
5. D 日特征过滤：换手率<=20%、量比<=1.3、振幅<=7%（基于 TOP20 统计）
6. 仓位：40% 上限
