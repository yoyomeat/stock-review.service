### 1.2 冰点守卫退出逻辑 Bug（已修复）

**问题描述**

`determine_cycle()` 中的冰点检测分两层：
1. Step 0（最高优先级）：三通道检测 → `is_freeze` 变量
2. Step 1（按 prev_label 分支）：`_handle_freeze()` 函数

当 `prev_was_freeze=True`（前日冰点）且守卫条件不满足时：
- Step 0 正确设置 `is_freeze=False`（守卫失败，应退出冰点）
- 但代码继续执行到 Step 1，调用 `_handle_freeze()`
- `_handle_freeze` 检查反弹条件（core≥30 & prof>50）和情绪修复条件（core≥30 & prof≤50）
- 两者都不满足时，**默认回到冰点**（`return '冰点期'`）

导致 `calc_op_v2` 中同样的守卫逻辑正确判断非冰点（`is_freeze=False` → 正常仓位），
但 `determine_cycle` 错误返回冰点标签，造成 `freeze=False` 与 `cycle_label='冰点期'` 不一致。

**受影响的4天**

| 日期 | cycle_label | freeze | core_sent | prof | 守卫结果 | 正确状态 |
|------|:-----------:|:------:|:---------:|:----:|:--------:|:--------:|
| 20250113 | 冰点期 | False | 28.1 | 39.0 | 失败(prof≥30) | 下降期第1天 |
| 20251119 | 冰点期 | False | 19.4 | 36.0 | 失败(prof≥30) | 下降期第1天 |
| 20260304 | 冰点期 | False | 25.9 | 35.0 | 失败(prof≥30) | 下降期第1天 |
| 20260515 | 冰点期 | False | 20.4 | 31.0 | 失败(prof≥30) | 下降期第1天 |

**根因**

`_handle_freeze()` 函数没有感知"守卫是否通过"的信息。当反弹和情绪修复条件都不满足时，
它无法区分"守卫通过但未恢复"（应延续冰点）和"守卫失败"（应退出冰点），一律默认回到冰点。

**修复方案**

符合架构原则1（单一修改点）：只修改 `quant/position.py` 一个文件，+3行。

```python
# 改动1：函数签名新增 guard_passed 参数
def _handle_freeze(prev_cycle_state, core_sent, prof, prev_sent, f3_score, gap_days, guard_passed=True):

# 改动2：默认返回逻辑改为守卫感知
# 守卫失败：反弹/情绪修复都不满足 → 转下降期（不再回到冰点）
if not guard_passed:
    return '下降期第1天', 1, 0.2, 0, ['冰点守卫退出(core_sent=%.0f,prof=%d)' % (core_sent, prof)]
# 守卫通过但反弹/情绪修复不满足 → 延续冰点
return '冰点期', 1, 0.0, 0, ['冰点延续(core_sent=%.0f,prof=%d)' % (core_sent, prof)]

# 改动3：调用处传递守卫状态
if '冰点' in prev_label:
    return _handle_freeze(prev_cycle_state, core_sent, prof, prev_sent,
                          f3_score, gap_days, guard_passed=is_freeze)
```

### 1.3 反弹D1→上升D1 跳级分析（确认无问题）

**现象**：18天从反弹确认期第1天直接跳到上升期第1天，似乎绕过了"反弹D2需prof≥60"的规则。

**分析结果**：全部17个转换由 `_handle_bounce_confirm()` 正确处理。

机制：反弹D1的次日在函数内部就是D2（`cd = prev_day + 1 = 2`），满足 `prof≥60` 就升级。
上升期的 day 重置为1。

```
反弹确认期第1天 (day=1)
  ↓ 次日
_handle_bounce_confirm(prev_day=1, prof=X)
  → cd = 2 (D2)
  → if cd == 2 and prof >= 60:
      return '上升期第1天', day=1  (上升期重新计数)
```

**数据验证**

| 反弹D1次日去向 | 笔数 | 占比 | 条件 |
|:---:|:---:|:---:|------|
| → 上升期D1 | 17 | 41% | prof≥60（min=60, max=83, mean=71.1）|
| → 下降期D1 | 14 | 34% | 断崖/阴跌/core崩盘/超时 |
| → 反弹D2 | 7 | 17% | prof在50~60之间，维持 |
| → 冰点期 | 3 | 7% | 三通道触发 |

prof≥60 的17个全部升级，prof<60的24个全部不升级。规则精确匹配。

**结论**：不收紧，尊重市场。

### 5.5 V4 核心机制补充：D-1 Pool 反馈

**来源**：scripts/pure_mainline_v3.py + PROGRESS_20260604_pure_mainline_debug.md §3.4

**机制**：
- 每日计算 mainline_pool 内个股的日均涨幅（D-1 close → D close）
- 均涨 > DEGRADED_AVG_RET_THRESHOLD(3%) → degraded 重置为 0
- 均涨 <= 3% → degraded += 1
- degraded >= DEGRADED_EXIT_DAYS(2) → 清仓退出

**与生产代码差异**：
- 生产版（信号驱动）：有 CONC 信号 → reset degraded，无信号 → +1
- V4（数据驱动）：pool 均涨 > 3% → reset，否则 +1

**影响**：tracker.update() 签名需变更新增 today_prices、prev_prices 参数，所有调用方需适配。

### 5.5 V4 核心机制补充：D-1 Pool 反馈

**来源**：scripts/pure_mainline_v3.py + PROGRESS_20260604_pure_mainline_debug.md 3.4节

**机制**：
- 每日计算 mainline_pool 内个股的日均涨幅（D-1 close → D close）
- 均涨 > DEGRADED_AVG_RET_THRESHOLD(3%) -> degraded 重置为 0
- 均涨 <= 3% -> degraded += 1
- degraded >= DEGRADED_EXIT_DAYS(2) -> 清仓退出

**与生产代码差异**：
- 生产版（信号驱动）：有 CONC 信号 -> reset degraded，无信号 -> +1
- V4（数据驱动）：pool 均涨 > 3% -> reset，否则 +1

**影响**：tracker.update() 签名需变更新增 today_prices、prev_prices 参数，所有调用方需适配。
