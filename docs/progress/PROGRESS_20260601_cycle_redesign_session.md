## 一、pool_state bug 修复（已完成）

### 问题
`compute_strong_pool(date_str=当天)` 选出当天5日涨幅TOP10 → `compute_pool_state` 看当天涨跌 = 循环论证。97%日期都是"大涨"，信号无用。

### 设计意图
D 日看 D-1 强势股池在 D 日的反馈 → 判断最灵敏资金有无跑路

### 修复
| 文件 | 改动 |
|------|------|
| `quant/anchor_monitor.py` | 新增 `compute_prev_pool_state()` — 取 D-1 强股池代码，查 D 日 CSV 算当日表现 |
| `quant/review_new.py` | pool_state 改用 D-1 池子 + D 日数据计算；review JSON 新增 `strong_pool` 字段存储当日池子代码+ret5 |
| `quant/meta_builder.py` | `build_meta` 输出新增 `strong_pool` 字段 |

### 数据流
```
D 日 review:
  1. compute_strong_pool(D) → D 的强股池 → 存入 strong_pool（供 D+1 使用）
  2. 从 prev_meta 读 D-1 的 strong_pool
  3. compute_prev_pool_state(D-1池, D日CSV) → D-1 强股在 D 的表现 → pool_state
  4. 首次运行（无 D-1 数据）→ fallback 到旧逻辑
```

### 验证
- pytest: 51 passed
- 单日复盘 20260529: strong_pool=10只股票，pool_state 输出正常
- 需要连续两天运行才能看到完整效果（D-1 池子需要前一天的 review 数据）

## 三、反弹确认期框架（已定稿）

### 核心变更
**删除**冰点→上升直接路径（暴力反转），所有冰点恢复**统一走反弹确认期**。

### 恢复条件（进入反弹确认期）
- core_sent ≥ 30
- prof > 50
- 恢复 ≥ 15（core_sent - 前日core_sent）

不满足 → 直接下降期（12个假恢复全部被拦截）

### 反弹确认期升级规则

| 时间点 | 条件 | 结果 |
|--------|------|------|
| D+2 | prof ≥ 60 | → 上升期（快速确认） |
| D+3+ | prof ≥ 50 且 core_sent ≥ 45 | → 上升期（延迟确认） |
| D+3+ | core_sent < 30 | → 下降期（崩盘，但可能误杀二次探底） |
| D+5 | 超时 | → 下降期 |

最少2天（D+1进入 + D+2首次评估），最多5天。

### prof + core_sent 双维度分析

**发现**：core_sent 单日波动比 prof 还大，单日 core 阈值无法区分真假反弹。

**最佳规则**：`D+2 prof≥60 或 (D+3 prof≥50 且 core_sent≥45)`
- 精确率 77%，召回率 83%

**D+2 prof≥60 快速路径**：6/6 全部正确（100%精确率）

### 全量模拟结果（338天，35个冰点段落）

| 指标 | 值 |
|------|:--:|
| 精确率 | 85% (11/13) |
| 召回率 | 69% (11/16) |
| 未恢复正确拦截 | 14/14 (100%) |

### 5个"漏掉"的真实上升
全部是**二次探底模式**：第一次反弹失败→回冰点→第二次才是真正上升。
冰点判断最优先，系统自动回到冰点状态等第二次恢复，最终能捕获。

### CONC 信号定位
- 冰点期 CONC：新主线启动信号（但数据中 CONC 信号在 review JSON 中为空，需确认数据源）
- 反弹确认期 CONC：确认信号（prof≥55 + CONC → 升级上升）
- 下降期 CONC：抱团指引，不作为上升标志
